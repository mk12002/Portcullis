P0 R1 · pwn-request — CRITICAL severity, HIGH confidence (escalated: job reachable from an untrusted trigger)
.github/workflows/vulnerable.yml:21 · jobs.triage.steps[0] · job triage

Job 'triage' runs on pull_request_target (secrets and a privileged token available) and checks out PR-head code — attacker-controlled code executes in a privileged context (pwn-request pattern).

trigger pull_request_target + checkout of PR head at step 'actions/checkout@v4'

Remediation: Split the workflow: handle untrusted PR code under the unprivileged pull_request event, and keep pull_request_target jobs from checking out PR-head refs. If PR code must be processed, do it without secrets and with permissions: read-all or less.

P0 R2 · expression-injection — CRITICAL severity, HIGH confidence (escalated: job reachable from an untrusted trigger)
.github/workflows/vulnerable.yml:25 · jobs.triage.steps[1].run · job triage

Untrusted context 'github.event.pull_request.title' is interpolated directly into a run script in job 'triage'. Its value is expanded before the shell parses the line, so crafted input becomes part of the command.

echo "PR title ${{ github.event.pull_request.title }}"

Remediation: Route the value through env: and reference it as a quoted shell variable, e.g. env: TITLE: ${{ <expr> }} then run: echo "$TITLE". The shell then receives the value as data, never as command text.

P0 R3 · unpinned-third-party — CRITICAL severity, HIGH confidence (escalated: job reachable from an untrusted trigger)
.github/workflows/vulnerable.yml:29 · jobs.triage.steps[3].uses · job triage

Third-party action 'example-org/super-linter' is pinned to a mutable reference (@v3). A compromised or retagged release changes what this pipeline executes.

uses: example-org/super-linter@v3

Remediation: Pin to a full commit SHA (uses: owner/action@<40-hex-sha> with a version comment) and update via a dependency bot; tags and branches are mutable.

P0 R5 · secret-echoed — CRITICAL severity, HIGH confidence (escalated: job reachable from an untrusted trigger)
.github/workflows/vulnerable.yml:27 · jobs.triage.steps[2].run · job triage

Secret(s) FIXTURE_FAKE_WEBHOOK_TOKEN are written to the job log by an echo/print in job 'triage'. Log masking is best-effort and fails on transformed values.

echo "webhook token ${{ secrets.FIXTURE_FAKE_WEBHOOK_TOKEN }}"

Remediation: Never print secret expressions; pass secrets via env: to the consuming process and rely on masked, non-printed usage.

P0 R5 · secret-untrusted-context — HIGH severity, MEDIUM confidence (escalated: job reachable from an untrusted trigger)
.github/workflows/vulnerable.yml:27 · jobs.triage.steps[2] · job triage

Job 'triage' uses repository secrets while reachable from an untrusted trigger (workflow triggered by pull_request_target). Combined with attacker-influenced execution this is the secret-exfiltration setup.

Remediation: Move secret-using work to a workflow that runs only on trusted events, or gate it behind environment protection rules with required review.

P0 R6 · curl-pipe-shell — HIGH severity, HIGH confidence (escalated: job reachable from an untrusted trigger)
.github/workflows/vulnerable.yml:31 · jobs.triage.steps[4] · job triage

Step 'install tool (unverified remote install; inert example domain)' pipes a remote download directly into an interpreter — the pipeline executes whatever the remote host serves, unverified.

Remediation: Download to a file, verify a pinned checksum (sha256sum -c) or signature, then execute; or install from a pinned package.

Methodology. Portcullis statically parses pipeline definitions into a normalized model (triggers, permissions, jobs, steps) and evaluates platform-agnostic rules R1–R6 against it. Findings inside jobs reachable from untrusted triggers are escalated one severity level (marked ↑) — the same misconfiguration is more dangerous where attacker-controllable input can reach it. Pipeline files are never executed and no network access occurs at scan time.

Limitations.
  • Static YAML/structure analysis cannot always prove that untrusted input actually reaches a sink at runtime — confidence levels mark that honestly.
  • Reusable/called workflows are followed shallowly: the reference is analyzed, not the called workflow's content.
  • Jenkinsfile (Groovy) parsing is best-effort structural extraction; findings there are capped at MEDIUM confidence.
  • High-entropy plaintext-secret detection has false positives (hashes, opaque IDs); such findings carry LOW confidence. Detected values are redacted everywhere.
  • A clean scan is evidence of hygiene, not proof of security.
